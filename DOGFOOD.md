# Dogfooding: Zyntry Verdict reviews itself

The court's own mechanism is applied to the Zyntry Verdict codebase. Before
trusting the engine, run the engine through the courtroom with the project's
own test suite as the sealed standard.

## The loop

```bash
# 1. Mirror the current source and test suite into the self-check case
node scripts/dogfood/snapshot.mjs

# 2. Open the courtroom on the current engine (live model provider)
node --experimental-strip-types packages/cli/src/index.ts run cases/zyntry-self/case.json

# ...or a wiring check without spending credits
node --experimental-strip-types packages/cli/src/index.ts run cases/zyntry-self/case.json --provider mock
```

## How it stays honest

- `cases/zyntry-self/repo/src/` is a mirror of `packages/engine/src/`. It is
  gitignored and regenerated by the snapshot script.
- The sealed standard is the project's own test suite, mirrored into
  `tests/suite/`. Courtroom agents can neither read nor run it.
- The hidden launcher executes the suite against the sandbox copy, so any
  edit an agent proposes is judged by the real tests.
- A dogfood verdict only counts when the run made real model calls. A
  zero-call record is a mock rehearsal, not a review. We say this because
  our own Nov 8 record turned out to be exactly that: a rehearsal run
  recorded before the live wiring existed. It has been retired.

| Nov 24, 2026 | `1c46aa6` + sandbox filter + container fixes | `@cf/zai-org/glm-4.7-flash` | `unresolved`, second harness timeout caught | 32 | 9 raised, 2 open objections | 0 |

What the first run caught was a harness bug, which is the dogfood working.
The court refused to certify the engine because the sealed standard kept
failing. Manual reproduction showed why: the standard's launcher was killing
the engine suite at a 55-second timeout, and the suite needs 60 to 90
seconds. The engine's own 103 tests were green. The dogfood wiring was
broken, and the courtroom surfaced it instead of silently passing.

The second run caught a second timeout bug the same way: with the first cap
raised, the sealed suite ran under heavy machine load and was killed at
240 seconds with zero output. Manual runs show the suite passes 88 of 88 in
about 50 seconds warm. Both caps are now 480 and 600 seconds
(commit `c58e512`). The court refused certification twice, correctly both
times: the standard itself kept failing, and it was the harness, not the
engine. That is what a sealed standard is supposed to do.

A clean-window run to completion is queued behind the benchmark tracks.

The committed case record, meaning the full transcript of every proposal,
rejection, claim, evidence record and hidden-suite execution, lands in
`docs/demo-records/` when the run closes.

## Verdict semantics

- `resolved-verified`: the engine survived its own sealed test suite under
  adversarial review, with evidence-cited claims.
- `unresolved`: the suite fails or the claims do not settle. The record
  shows what broke and why.

This is the same discipline we sell: no change ships on faith, including
ours.
